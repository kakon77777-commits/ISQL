# ISQL-MEM v0.3 Spectral Coordinate Compaction Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Compile verbose `isql.semantic-analysis/v0.2` coordinates into a persistent, versioned sparse spectral packet that reduces per-memory runtime representation size while preserving stable address identity, semantic-coordinate fidelity, and R4 exact-source boundaries.

**Architecture:** Keep verbose semantic analysis as auditable authoring/provenance data. Add an append-only shared spectral registry that interns repeated strings to compact integer IDs and emits `SpectralPacket` objects containing sparse integer coordinate arrays and relation tuples. Add a `spectral` memory profile whose R1/R2 layers use packets, while R3 retains provenance and R4 retains the exact-source contract.

**Tech Stack:** Python 3.11+, standard library only, unittest, UTF-8 JSON, SHA-256, current `isql-core-runtime` package.

## Global Constraints

- `ISQL-ADDR` identity must not depend on semantic analysis, registry state, or decoder model.
- Existing `baseline` and `semantic` profile codes remain unchanged.
- v0.2 memory records must remain readable.
- The spectral registry is append-only: existing numeric IDs never change meaning.
- Packet decoding must use the recorded registry revision, not fuzzy/AI inference.
- R4 exact recovery remains source-contract-only.
- Compression reporting must distinguish packet bytes from registry growth bytes; one-shot cold-start overhead may be larger than verbose JSON and must be reported honestly.
- No external embeddings, AI API, or database dependency is required.
